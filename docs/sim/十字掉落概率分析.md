## 1. 四件十字物件

十字形 `SHAPES.cross = [[0,1],[1,0],[1,1],[1,2],[2,1],[1,3]]`（6 格，3×4 包围盒，`game.js:524` 起的 `SHAPES`）。

| id | 名称 | 稀有度 | 基础价值 | 可出现的柜 | 定义行 |
|---|---|---|---|---|---|
| `gold_drone` | 镀金勘测机 | 大金 dajin | ¥29,000 | 仅 limited（限时柜） | `game.js:678` |
| `solar_array` | 炎阵列板 | 炎金 yanjin | ¥41,000 | 仅 limited | `game.js:685` |
| `vein_core` | 血脉能源芯 | 小红 xiaohong | ¥58,000 | sealed（密封柜）+ limited | `game.js:693` |
| `void_ingot` | 虚空赤锭 | 大红 dahong | ¥175,000 | 仅 limited | `game.js:696` |

- common（普通柜）/ rare（精选柜）池里**没有**十字物件 → 概率 **0**（`tiers` 字段限制 + 这两种柜 `mult` 里金红稀有度为 0 或极低且池内无十字）。
- sealed 里**只有 `vein_core` 一件**十字（小红池 9 件里的 1 件）；limited 里四件都可能出。
- 十字物件**没有任何保证 / 保底掉落**：它只是各稀有度池里的一件普通物品。图鉴（`renderCodexModal`，`game.js:1647`）只显示名称 / 稀有度 / 基价；对 `index.html` / `game.js` 全文搜过 `必出 / 保证 / 必定 / 一定出 / 稳出`，**没有任何文案声称十字（或任何物品）必出**（唯一的「保底」字样是帮助里「热手/冷手」的"软保底，不送大红"，与十字无关）。

## 2. 掉落是怎么生成的（`rollLoot`，`game.js:1229`）

1. **件数**：`CRATE_TIERS[tier].count`（sealed 5–8 件，limited 6–9 件；蜜月期 `HONEYMOON.COUNT` 覆盖，`game.js:398`）。
2. **每件先抽稀有度** `weightedPick`（`game.js:1193`）：权重 = `RARITIES[r].weightBase` × `CRATE_TIERS[tier].mult[r]`（`game.js:39`）× `pityFactor`（连亏软保底，`game.js:1178`）× `rareBoostFactor` × `honeymoonWeightMult`（`game.js:1168`）× `auctionHallWeightMult`（高级厅 +3%/+4%，`game.js:1845`）。
   - sealed `mult`：dahong 0.55 / xiaohong 0.6 / yanjin 0.7 / dajin 0.8 / xiaojin 0.8 / pink 1 / purple 1.3 / blue 1.2 / green 0.6 / white 0。
   - limited `mult`：dahong 3 / xiaohong 1.3 / yanjin 0.65 / dajin 0.55 / xiaojin 0.55 / pink 0.85 / purple 1.7 / blue 1.4。
3. **再从该稀有度 + 该柜的池里挑具体物品** `poolFor(rarity, tier)`（`game.js:705`），挑选时有「形状偏好」`pickDefFromPool`（`game.js:1264`）：sealed 22% 优先友好形状 / 68% 优先异形（cross 属于 `AWKWARD_SHAPES`，`game.js:553`），limited 14% / 78%；池内等概率。
4. 每件的价值 = `def.value × tierValueScale × jitter`（`game.js:1158`）；十字与其他同稀有度物品**同价**，没有额外加成。
5. 首开蜜月保底（`honeymoonGuaranteeRarity`，`game.js:1097`）替换第 1 件为紫/小金，池里没有十字。

sealed 单件抽到某稀有度的概率（无蜜月、无厅、无 pity）：dahong 0.289% / **xiaohong 0.894%** / yanjin 1.84% / dajin 2.80% / xiaojin 5.61% / pink 11.4% / purple 19.4% / blue 31.5% / green 26.3%。
小红池 9 件里 `vein_core` 占 1 件，再乘上形状偏好权重 → **每件 0.086%**，每柜 5–8 件 → 约 0.56%。

limited 单件稀有度：dahong 1.905% / xiaohong 2.338% / yanjin 2.063% / dajin 2.328% / xiaojin 4.656% / pink 11.7% / purple 30.6% / blue 44.4%。四件十字每件 0.20–0.25%，每柜 6–9 件。

## 3. 每柜概率（解析解 `analytic.js`，已用 250,000 柜蒙特卡洛交叉验证）

「P(≥1 十字)」= 一个柜至少出一件十字；「1/p」= 平均多少个柜出一次；「22/40 个柜都没出」= (1−p)^22 / (1−p)^40；「EV 占比」= 十字物件占该柜期望货值的比例。

### 3.1 常规（蜜月结束后，无厅）

| 柜 | P(≥1 十字)/柜 | 期望十字数/柜 | 1/p | 22 柜都没出 | 40 柜都没出 | EV 占比 |
|---|---|---|---|---|---|---|
| common 普通 | 0 | 0 | — | 100% | 100% | 0 |
| rare 精选 | 0 | 0 | — | 100% | 100% | 0 |
| **sealed 密封** | **0.557%** | 0.00558 | **≈180** | **88.4%** | **80.0%** | **1.00%** |
| **limited 限时** | **6.573%** | 0.0677 | **≈15.2** | **22.4%** | **6.6%** | **7.21%** |

（sealed 每柜期望货值 ≈¥34,685，其中十字 ≈¥346；limited ≈¥75,535，其中十字 ≈¥5,448。）
sealed 的唯一十字是 `vein_core`；limited 里单件分布：gold_drone 0.244% / solar_array 0.248% / vein_core 0.199% / void_ingot 0.212%（每件）。

### 3.2 按拍卖厅 / 蜜月状态（P(≥1 十字)/柜）

| 柜 | 状态 | 无厅 | 青铜厅 | 翡翠及以上（翡翠/白银/铂金/赤金） |
|---|---|---|---|---|
| sealed | 常规 | 0.557%（1/180） | 0.572%（1/175） | 0.576%（1/174） |
| sealed | 蜜月中（保底已用） | 0.856%（1/117） | 0.878%（1/114） | 0.885%（1/113） |
| sealed | 蜜月首开（保底待用） | 0.725% | 0.743% | 0.749% |
| limited | 常规 | 6.573%（1/15.2） | 6.738%（1/14.8） | 6.793%（1/14.7） |
| limited | 蜜月中 | 11.45%（1/8.7；`void_ingot` 被蜜月屏蔽 dahong） | 11.70% | 11.78% |
| limited | 蜜月首开 | 10.00% | 10.22% | 10.29% |

厅对 22/40 柜“都没出”的影响很小：sealed 常规 22 柜 88.4% → 88.1%（翡翠+），40 柜 80.0% → 79.4%；limited 常规 22 柜 22.4% → 21.3%，40 柜 6.6% → 6.0%。
连亏软保底（pity）略抬高 sealed：连亏 3/4/5/6 场时 P 为 0.601% / 0.634% / 0.658% / 0.678%（同时整体 EV 上升），limited 不变（limited 没有白/绿档，pity 把蓝及以上整体同比抬高，相对比例不变）。

蒙特卡洛核对（250,000 柜/格，`mc.json`）：sealed 常规 MC 0.570% vs 解析 0.557%；limited 常规 MC 6.571% vs 解析 6.573%；蜜月格同量级。`verify_game.js.json`（逐条对照）里 EV 与 EV 占比的 MC / 解析差都在 ±0.1 个百分点内。

## 4. 备选方案（均已用真实 `game.js` 补丁 + 250,000 柜 MC 验证；**NOT adopted**）

目标都是只动密封柜里「十字出现得太少」这一点，同时不改密封柜整体期望货值（EV）。三个补丁见 `cross-drop/A.patch`、`B1.patch`、`B2.patch`（对 `b3680fa` 的 `game.js`）。

| 方案 | 做法 | sealed P(≥1 十字)/柜（解析 / MC） | sealed EV/柜（解析 / MC） | sealed 十字 EV 占比 | limited P | 备注 |
|---|---|---|---|---|---|---|
| 基线（现状） | — | 0.557% / 0.533% | ¥34,685 / ¥34,799 | 1.0% | 6.573% | 1/180 |
| **A** 改权重 | `vein_core` 加 `w:{sealed:16}`（池内权重 16:1×8），并把 sealed 的 `mult` 调为 xiaohong **0.9624**、yanjin **0.55**、dajin **0.6286**、xiaojin **0.6286**（`solveA.js 0.05 8` 解出，使 EV 与现状相等）；同时 `pickDefFromPool` 支持 `def.w` | **5.00% / 5.01%**（1/20） | ¥34,686 / ¥34,807（EV 不变，−0.001%） | 9.1% | 不变 | 改动最大：动 `CRATE_TIERS.sealed.mult` + 抽取函数；小红整体变多（0.894% → 1.906%），需重测收支曲线 |
| **B1** 换形状 | sealed 小金 `gold_flute`(1×4, ¥11,500) 改成十字，`vein_core` 改成 1×4；十字池从小红(1/9)移到小金(1/8 且小金更常见) | 3.33% / 3.39% | ¥34,685 / ¥34,799（EV 不变） | 1.2% | 5.16%（limited 少了一件十字） | 十字变成 ¥11,500 的便宜货，limited 的 `vein_core` 变 1×4 |

## 5. 决定与后续

- **决定**：不改密封柜价值表 / 权重 / 形状；十字稀有可接受。等收集到**几百场**真实玩家的密封柜样本后，再用真实比例复议是否采用 A（或别的方案）。
- **数据来源**：release `20260926g` 起 `crate_open` / `round_settle` 埋点带 `loot_ids`（`"id:n,id:n"`，按 id 排序）。用下面的 SQL 在 D1 里算真实十字率，对比上表预期（sealed ≈ 0.56%/柜，limited ≈ 6.6%/柜；蜜月期更高，注意分开看 `honeymoon`）。

```sql
-- 真实十字出现率（按柜型）。排除评测会话：eval = 0 且 eval_tainted = 0
-- crate_open 事件的 tier 字段在 props 里；loot_ids 也在 props 里。
SELECT
  json_extract(props, '$.tier')                                   AS tier,       -- sealed / limited / common / rare
  honeymoon,
  COUNT(*)                                                         AS crates,
  SUM(json_extract(props, '$.loot_ids') LIKE '%vein_core:%')       AS vein_core,
  SUM(json_extract(props, '$.loot_ids') LIKE '%gold_drone:%')      AS gold_drone,
  SUM(json_extract(props, '$.loot_ids') LIKE '%solar_array:%')     AS solar_array,
  SUM(json_extract(props, '$.loot_ids') LIKE '%void_ingot:%')      AS void_ingot,
  SUM(   json_extract(props, '$.loot_ids') LIKE '%vein_core:%'
      OR json_extract(props, '$.loot_ids') LIKE '%gold_drone:%'
      OR json_extract(props, '$.loot_ids') LIKE '%solar_array:%'
      OR json_extract(props, '$.loot_ids') LIKE '%void_ingot:%')   AS any_cross,
  ROUND(100.0 * SUM(   json_extract(props, '$.loot_ids') LIKE '%vein_core:%'
                    OR json_extract(props, '$.loot_ids') LIKE '%gold_drone:%'
                    OR json_extract(props, '$.loot_ids') LIKE '%solar_array:%'
                    OR json_extract(props, '$.loot_ids') LIKE '%void_ingot:%') / COUNT(*), 3) AS any_cross_pct
FROM events                       -- 表名按 tools/analytics/schema.sql 实际为准
WHERE ev = 'crate_open'
  AND eval = 0 AND eval_tainted = 0
  AND econ = 'econ-0925h'         -- 与当前经济版本一致；测试版 econ = 'test' 自然排除
  AND build >= '20260926g'        -- loot_ids 从该版本开始才有（build 为字符串，按字典序比较）
  AND json_extract(props, '$.tier') IN ('sealed', 'limited')
GROUP BY tier, honeymoon;
```

> 注意：`loot_ids` 超过 200 字符时会按「价值从低到高」丢弃低价 id（十字这类高价 id 不会被丢）；`LIKE '%vein_core:%'` 带冒号，避免误匹配前缀相近的 id。样本量几百柜时，sealed 的 0.56% 只对应 ≈1–3 次命中，统计上很稀疏——建议至少攒到 ≥1,500 个 sealed 柜再下结论（95% 置信区间才能把 0.56% 与 5% 区分开；要区分 0.5% 与 0.8% 则需更多）。

## 6. 复现

脚本都在 `docs/sim/cross-drop/`，用 `vm` 从 `game.js` 里抽取真实函数（默认读仓库根的 `game.js`，可用环境变量 `GAME_JS=<path>` 指向补丁后的副本）。无需安装依赖。

```bash
cd docs/sim/cross-drop
node report.js                 # 解析解：sealed / limited × 常规 / 蜜月 / 蜜月首开 × 各厅（p、1/p、22/40 柜都没出、EV 占比）
node mc.js 250000              # 蒙特卡洛，写 mc.json（4 种柜 × 厅 × 蜜月状态，约几分钟）
node verify.js 250000          # 当前 game.js 的 MC vs 解析逐条对照，写 verify_game.js.json
node solveA.js 0.05 8          # 解方案 A：目标 5%/柜、vein_core 池内权重 8 ⇒ 反推 sealed mult 使 EV 不变
# 验证备选方案（把补丁打到临时副本上，不改仓库）
for v in A B1 B2; do cp ../../../game.js /tmp/$v.js && patch /tmp/$v.js $v.patch && GAME_JS=/tmp/$v.js node verify.js 250000; done
```

文件：`lib.js`（抽取 + 种子随机）、`analytic.js`（解析模型）、`mc.js`、`verify.js`、`solveA.js`、`report.js`；`mc.json`、`verify_*.json` 为本次结果（250,000 柜/格，基于 `b3680fa`）；`A.patch` / `B1.patch` / `B2.patch` 是三个备选补丁。
> 提示：`verify.js` 会覆盖同目录下的 `verify_game.js.json`（用 `GAME_JS` 指向补丁文件时写 `verify_<名>.json`）；补丁基于 `b3680fa`，之后 `game.js` 若大改函数体需要手动调整补丁。
