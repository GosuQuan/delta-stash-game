# 仓储拍卖开箱 · 埋点方案（v0.2 · 商业化已审）

> 负责人：游戏用户体验运营设计开发 · 45 分钟一轮迭代 · 本版：2026-09-25 第 2 轮
> 接入清单：`docs/埋点接入清单.md`；接收端代码：`tools/analytics/`
> 核心问题：**线上真人的数据和 `docs/sim/results.md` 的模拟对不对得上。**
> 所有代码位置基于 `20260925g` 的 `game.js`，行号会漂移，以函数名为准。

## 0. 先定前提：怎么把数据收上来

现在游戏是 GitHub Pages 纯静态页，`window.__monetizationLog` 只存在玩家自己浏览器里，关页就没了。给两个方案：

### 方案 A（推荐）：Cloudflare Worker + D1 自建一个接收端
- 做法：一个几十行的 Worker 接 `POST /e`，把一批事件写进 D1（Cloudflare 的 SQLite）。前端攒批，用 `navigator.sendBeacon` 在离开页面时补发。
- 成本：Workers 和 D1 都有免费档（按请求数和写入行数计，具体额度以 Cloudflare 官网为准）。事件攒批发送，一场十来条事件只占 1 到 2 次请求，评测和小规模上线阶段预计不花钱。需要少权注册或登录一个 Cloudflare 账号，部署由 grok 或我来做。
- 好处：数据在我们自己手里，一场一行，直接写 SQL 按柜型算比值和赚钱概率，跟模拟表逐项对照；不加载第三方脚本，页面不变重，隐私说明也最简单。
- 代价：漏斗、留存图要自己写 SQL 或导出看，没有现成看板。

### 方案 B：PostHog Cloud（第三方产品分析）
- 做法：页面引入 PostHog 的 JS SDK，调用 `posthog.capture(事件名, 字段)`。
- 成本：有免费月额度（以官网价格页为准），超出按事件量计费。接入最快，半小时内能跑通。
- 好处：漏斗、留存、分群现成可用，适合看「玩家在第几场流失」。
- 代价：加载第三方脚本；默认会记 IP 和设置 cookie，需要手动关闭（`ip: false`、`persistence: 'localStorage'`、关闭自动采集）；数据在第三方。

### 两个方案共同的隐私规则
1. 不收任何个人信息。玩家 ID 是首次打开时生成的随机串（`pid`），存在 localStorage，清缓存即换新。
2. 不存 IP。方案 A 在 Worker 里不写 IP，最多只记国家代码；方案 B 关掉 IP 采集。
3. 帮助页加一句说明：「为了调平数值，游戏会匿名记录开柜和结算数据，不含个人信息」，并给一个「不参与统计」开关（存 localStorage，关了就完全不发）。
4. 评测模式 `?eval=1` 照常上报但打 `eval: true` 标记，分析时默认排除，内部测试不会污染真人数据。
5. 原始事件保留 90 天，之后只留按天汇总的表。
6. 已知限制：GitHub Pages、`workers.dev` 和 PostHog 在中国大陆访问都可能不稳定，这一阶段的数据会偏向海外和能正常访问的玩家。以后上微信或抖音小游戏时，改用平台自带的数据分析或国内的接收端。

## 1. 前端接法（两个方案共用）

新增一个 `track(ev, fields)`，和现有 `logMono` 分开（`logMono` 继续只管广告和内购）：
- 自动带上公共字段（见下），写入本地队列 `window.__analyticsLog`（环形，≤300，调试用）。
- 队列攒满 10 条或每 30 秒发一次；`pagehide` 和 `visibilitychange` 变为 hidden 时用 `sendBeacon` 补发。
- 开关 `FEATURES.ANALYTICS_ENABLED` 加一个 `ANALYTICS_ENDPOINT`。接收端没建好前把地址留空，事件只进本地队列，这样埋点代码可以先合进去，不影响线上。
- `?mono=1` 调试条同时显示 `track` 事件，方便测试玩家核对。

## 2. 公共字段（每条事件都带）

| 字段 | 含义 | 来源 |
|---|---|---|
| `schema` | 埋点版本号，从 1 开始 | 常量 |
| `ev` | 事件名 | |
| `ts` | 客户端时间戳（毫秒） | `Date.now()` |
| `pid` | 匿名玩家 ID | localStorage 随机串 |
| `sid` | 本次会话 ID（每次打开页面新生成） | 内存 |
| `build` | 版本号，如 `20260925g` | `version.json` / `?v=` |
| `round` | 当前第几场 | `round` |
| `cash` / `peak` | 当前现金 / 峰值现金 | `cash` / `peakCash` |
| `hall` | 当前拍卖厅 id（无厅为 null） | `activeAuctionHall()` |
| `grid` | 仓库边长（5 到 8） | `gridSize` |
| `honeymoon` | 是否在新手保护期 | `honeymoonActive()` |
| `econ` | 经济数值版本，如 `econ-0925h` | 常量 |
| `save` | 存档 ID，新开档换新 | 存档 |
| `eval` | 这一条是否发生在评测模式 | `evalMode` |
| `eval_tainted` | 存档是否进过评测（可能有加过的钱或免费尺寸），只有新开档清零 | 存档 |
| `dev` | `mobile` / `pc`，加视口宽度分档（≤360、≤420、≤820、更宽） | UA 与 `innerWidth` |

## 3. 事件清单

### 3.1 `crate_open` 开柜
- 位置：`openCrate()`，扣完租金、`rollLoot` 出货之后。
- 字段：`tier`（common / rare / sealed / limited / 以后的专属柜 id）、`rent_base`（标价，不含蜜月折扣）、`rent_paid`（实付，含蜜月折扣、装箱奖励 88 折、免费券为 0）、`discount`（none / honeymoon / perfect_pack / free_token）、`rent_cash_pct`（实付租金占开柜前现金的比例）、`items`（出货件数）、`rarity`（各品质件数，如 `{white:2,blue:3,purple:1}`）、`daily_left`（该柜今日剩余次数，限时柜和专属柜才有）。
- 用途：`rent_cash_pct` 用来把玩家分成「稳健档」（≤40%，和模拟假设一致）和「激进档」，只拿稳健档跟模拟比节奏。

### 3.2 `round_settle` 结算
- 位置：`extract()`，算完 `net` 之后。
- 字段：`tier`、`rent_paid`、`loot_value`（卖出货值，已含守住挑战的涨跌）、`packed_value`、`discard_n` / `discard_value`（丢弃件数和货值）、`util_pct`（仓库占用）、`perfect_pack`（是否触发）、`perfect_bonus`、`empty_refund`（空柜退款）、`net`、`challenges`（本场触发几次守住）、`challenge_ok`（其中答对几次）、`dur_s`（本场从开柜到结算的秒数）。
- 用途：对照模拟的主表。比值 = (`loot_value` + `perfect_bonus`) ÷ `rent_paid`，赚钱 = `net > 0`。按 `tier × honeymoon × grid` 分组，和商业化方案 4.1、4.2、5 的目标区间逐格对照。

### 3.3 `challenge_result` 守住挑战
- 位置：`runItemChallenge()` 的 `finish()` / `finishProtect()`，`runFollowBallChallenge()` 的 `finishOk()` / `acceptFailSettle()` / `finishProtect()`。
- 字段：`kind`（math / logic / follow_ball）、`rarity`、`value_before`、`value_after`、`result`（up / keep / down）、`hit_rate`（跟随球命中率）、`protect`（none / key / charge / ticket）、`answer_ms`（答题用时）。
- 用途：模拟假设鉴宝答对 70%。真人答对率如果明显偏离，比值偏差先从这里解释，再去怀疑货池。

### 3.4 `bankrupt` 破产
- 位置：`checkBankrupt()` 判定破产、弹出面板时。
- 字段：`cash`、`total_pnl`、`restructure_avail`（今天还能不能重组）、`last_tier`（最后一场开的柜子）、`rounds_since_start`（本档第几场，区分前 15 场和第 16 场以后）。

### 3.5 `restructure` 重组 / `new_save` 新开档
- 位置：`applyRestructure()`；以及「新开档」按钮的处理函数。
- 字段：`grant`（¥5,850）、`restructure_n`（本档累计重组次数）；新开档记 `prev_round` 和 `prev_peak`。
- 用途：破产以后是重组继续玩，还是新开档，还是直接走人（配合 3.9 看）。

### 3.6 `hall_unlock` 拍卖厅解锁
- 位置：`checkAuctionHalls()` 里新解锁一个厅时（写 `addLog` 的那一行旁边）。
- 字段：`hall_id`、`hall_peak`（解锁门槛）、`rounds_to`（本档第几场到达）、`play_min`（本档累计游玩分钟）、`restructure_n`。

### 3.7 `peak_reach` 节奏节点
- 位置：`notePeakCash()`，峰值首次越过 8 万、30 万、100 万时各发一次。
- 字段：`mark`（80000 / 300000 / 1000000）、`rounds_to`、`play_min`、`style`（本档到此为止 `rent_cash_pct` 的中位数，≤0.4 记为稳健）。
- 用途：直接对照「到 8 万 35–50 场、到 30 万 100–150 场」。8 万和翡翠厅门槛重合，但 30 万没有对应的厅，所以单独发。

### 3.8 `warehouse_expand` 扩容 / `organize` 整理
- 扩容位置：`applyExpand(nextSize, via)`。字段：`from`、`to`、`via`（cash / iap / eval）、`cost`、`cash_before`、`cost_cash_pct`。
- 整理位置：`requestOrganize()` 和 `speedOrganizeAll()`。字段：`source`（daily_free / key / iap）、`packed_n`、`packed_value`、`keys_left`。
- 用途：扩容改成分级价以后，看真人是否在「扩容价 ≤ 现金 40%」时买，和模拟对扩容时机的假设对不对得上；整理用钥匙的频率决定钥匙的定价。

### 3.9 `session_start` / `session_end` 会话
- `session_start` 位置：`loadGame()` 之后、首屏可操作时。字段：`is_new`（是否新档）、`days_since_first`（距首次打开几天）、`days_since_last`。
- `session_end` 位置：`pagehide`，以及 `visibilitychange` 变为 hidden（手机切后台时 `beforeunload` 经常不触发，所以不靠它）。字段：`session_rounds`（本次玩了几场）、`session_s`、`state`（idle / revealing / packing / bankrupt_modal，也就是离开时停在哪一步）、`last_net`（最后一场净额）、`streak`（离开时连胜或连败几场）。
- 用途：回答「离开时处在第几场」。重点看两件事：一是破产面板、连亏后离开的比例；二是新玩家在第几场之前流失最多，是否落在蜜月刚结束的第 6 到 8 场。

## 4. 怎么跟模拟对照（接收端建好后的第一批查询）

1. **各柜比值与赚钱概率**：`round_settle` 按 `tier` 分组，排除 `eval` 和 `honeymoon`，算比值均值、分位数和 `net > 0` 的比例，填进商业化方案的目标区间表旁边一列。
2. **鉴宝答对率**：`challenge_result` 算真人答对率。偏离 70% 时，用真人答对率重跑一遍模拟再对比，避免误调货池。
3. **节奏**：`peak_reach` 只取稳健档，算到 8 万和 30 万的场数分布，对照 35–50 场和 100–150 场。
4. **破产率**：`bankrupt` 按 `rounds_since_start ≤ 15` 和 `≥ 16` 分组，除以对应区间的活跃档数，对照 10% 和 15%。
5. **装箱**：`round_settle` 的 `discard_n`、`util_pct` 按 `grid` 分组，看真人装箱是否比模拟的贪心装箱更好或更差，这决定双联柜和扩容定价准不准。
6. **样本量**：比值的波动很大，每个柜型攒够几百场非蜜月结算之前只看方向，不据此改数值。

## 5. 已定决策（2026-09-25 商业化拍板）
1. 用方案 A：Cloudflare Worker 加 D1。埋点代码先接进游戏，`ENDPOINT` 留空，只进本地队列；接收端等少权有 Cloudflare 账号后部署。
2. 帮助页文案：「为了调平数值，游戏会匿名记录开柜、结算等玩法数据，不含姓名、账号、IP 等个人信息，可以随时关闭。」开关叫「参与匿名统计」，默认打开。
3. `tier` 直接用柜子 id，另加 `tier_group`，取值 `general`（通用柜）或 `hall`（拍卖厅专属柜）。
4. 公共字段加 `econ`，记经济数值版本（今天是 `econ-0925h`），只在调数值时改，与发版号分开。
5. 免费券开柜（`rent_paid = 0`）和空柜退款不参与比值计算。
6. 评测模式照常上报，每条带 `eval = 1`，所有对照查询默认排除。
8. 公共字段另加 `eval_tainted`：存档进过评测记 1，对照查询同时排除 `eval = 1` 和 `eval_tainted = 1`；存档里的东西不回收。
7. 公共字段另加 `save`（存档 ID，新开档换新），破产率和节奏按存档而不是按玩家算。
